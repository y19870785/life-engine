# 体验优先的 Soul Continuity 规划校准（草案）

状态：`PLANNING_DRAFT / NOT_EXECUTION_AUTHORIZATION`。编制基线：`main@5cd993c1d9d286e3d903e36be54d3650446b5deb`（PR #54 合并提交）。本文件提出产品验收与推进顺序的校准，不改写[现行 Soul Continuity 开发计划](SOUL-CONTINUITY-DEVELOPMENT-PLAN.md)、[阶段内自主开发方案](CODEX-STAGE-AUTONOMY-PLAN.md)或已冻结的技术合同；不授权 Runtime、Schema、Prompt、Host、发送或下一阶段实施。若决定调整正式 Roadmap，先按[路线图变更规则](LIFE-ENGINE-DEVELOPMENT-ROADMAP.md)完成独立架构审核与用户确认。

## 1. 目标与偏差

用户的原始目标是：长期相处后，Agent 能自然地记得共同经历，形成有延续的关系，并拥有前后一致的自己的世界。这里的“活人感”是可观察的交互质量，不是意识、真实生活经历或永不出错的承诺。Agent 的世界可以是清楚标识的虚拟日常；它不能把生成的日常当作真实外部事实，也不能把 Roleplay World 混入 Original Soul。

现行规划保留了这一方向，但近阶段主要产出身份、持久化、准入和故障证明。现有 World Memory Core 尚未自动进入真实每轮对话；M1-A 的已合并探针也只达到 `E0_SYNTHETIC_PARTIAL / M1-A_PRIMITIVE_GATE_PENDING`。因此“技术上更能证明是同一个 Soul”和“用户已经感到它在持续生活”必须分别验收。不能用前者替代后者，也不能为了追求后者绕开前者的正式放行门禁。

## 2. 产品验收：先写出能亲自感受到的场景

| 场景 | 可观察行为 | 必须拒绝的行为 |
| --- | --- | --- |
| 共同经历跨日延续 | 用户前一天提到面试；第二天在合适语境下，Agent 能准确接续，并知道自己从何处得知 | 无依据地主动追问、编造面试结果或把其他 World 的剧情当作共同经历 |
| 纠正与遗忘 | 用户纠正日期或要求忘记一项内容；后续回答采用新事实，正常检索不再带出已忘正文 | 派生摘要、缓存或旧备份把错误/已忘内容重新注入对话 |
| 自己的世界连贯 | Agent 能解释此刻的虚拟活动、地点、近期事件及变化来源；跨会话不无故跳变 | 将预设作息或随机选择说成真实发生且已被证实的经历 |
| 关系随相处变化 | 记住有来源的共同事件、偏好和重要纠正，表达随关系发展而变化 | 根据单次模型发挥捏造共同历史、信任或亲密程度 |
| 合适的主动性 | 有待跟进事项且联系条件满足时才提出相关话题；无合适理由时保持安静 | 定时模板式问候、重复追问，或把调度唤醒当作发送授权 |
| 同一个 Agent 继续生活 | 重启、模型变化或受控迁移后的身份和历史可核对；无法判断时明确停下 | 仅凭名称、Prompt 自称或恢复的数据库宣称合法 continuation |

第一轮体验评估用一个受控 Soul World、一名用户、数次跨日会话和明确的虚拟日常即可；同时保留跨 World 泄漏、错误恢复、纠正及遗忘的反例。记录每次回答使用了哪些事实、其来源、当时的世界状态，以及用户主观上是否感到自然。主观评价与机械事实检查分开保存；不把示例对话当成真实 Host 验收。

## 3. 两条并行的工作线

**可信连续性线**沿用 M1 → M1.x → M2 的正式门禁。M1 聚焦首个体验闭环真正需要的身份、来源、准入与恢复条件；M1.x 判断 continuation、fork、mismatch、unknown。M1-A 的旧入口绕过和管理域回滚缺口未解决前，不开放 active Soul 写入，也不把合成探针提升为产品准入。扩大原语或部署范围须另行审定，不以“体验优先”为由降低证明要求。

**体验证据线**可以先行定义场景、人工演示稿和失败分类，尽早检验“记得、变化、世界连贯”是否真的改善相处体验。现阶段这只是规划与评估材料。若需要离线交互原型、模型调用、测试代码或从真实聊天导入数据，须另立有界任务：使用隔离合成数据，明确数据来源和可见范围，不改产品真源、不接真实 Host、不自动发送；原型结果只证明体验方向，不能作为 M1/M1.x/M2 的通过证据。

## 4. 建议推进顺序与出口

1. **X0：体验合同与现状基线。** 从上表选 6–8 个具体场景，写清输入事实、期望行为、反例、观察方法和用户评价问题。用现有能力走一遍，区分“已有 Core 能力”“手工拼接”“尚未实现”。交付可复核的场景卡与基线记录；这一步不改 Runtime。
2. **X1：隔离体验试验。** 在单独授权后，用合成经历和明确标注的虚拟日常做跨会话演示，检验记忆选取、世界状态与表达是否自然。每次演示保留事实来源和失败记录；达到体验价值才据此收窄正式 M2/M3 的最小范围。X1 不申请正式 Soul continuation、Host 发送或产品数据写入资格。
3. **X2：可信底座最小收口。** 继续 M1-A 未证明的原语、准入和管理域问题，随后按冻结合同推进 M1 与 M1.x。若目标部署无法提供受信独占且不可整体回滚的管理域，停止该候选并走架构变更；不为赶体验里程碑默认放行。
4. **X3：首个正式可用闭环。** 通过前置门禁并获独立实施授权后，优先交付 M2 的最小“记录 → 持久化 → 检索 → 只读 Prompt 投影 → 纠正/遗忘”闭环，覆盖跨会话/跨日和 World 可见范围。验收既看机械正确性，也让用户实际比较基线与新行为；不一次性实现全部记忆分类和排序策略。
5. **X4：关系与自己的世界。** 在 M2 稳定后推进有来源的共同经历、关系记忆和自我叙事，再让虚拟日常、近期事件与 Living 消费同一状态。真实主动联系、媒体和语音各自保留 Host/发送/回执门禁；“模型说得自然”不是外部交付证明。

X0/X1 是产品方向校验，不改变正式 M1 → M1.x → M2 → M3 → M4 的依赖顺序。若试验表明必须让 M2 产品代码早于 M1.x 上线，应先提出具体路线图与架构变更，接受独立审核，不在本草案中偷换顺序。

## 5. 用户逐步试用：每个切片都有可操作的出口

不等整条 Soul Continuity 路线完成才第一次让用户试。每个获授权的功能切片在开发任务中同时列出“用户怎样亲自试、能观察到什么、已知不能证明什么”；功能和测试入口一起交付。先在隔离环境试用，再随证据扩大范围。试用反馈可改变下一切片的产品优先级，但不能替代机械验证或自动提升授权。

| 试用层级 | 用户可以做什么 | 开放条件与结论边界 |
| --- | --- | --- |
| T0：场景共评 | 阅读 X0 场景卡，指出哪种接续、世界状态或主动性像/不像目标 Agent | 现在即可准备；这是需求与体验基线，不是功能 PASS |
| T1：离线交互样机 | 在隔离数据里亲自进行跨会话对话，试“记住—纠正—接续”和虚拟日常一致性 | X1 另获明确授权并标注合成数据、模型/人工拼接部分；不连接产品真源或真实 Host |
| T2：本地 Core 沙箱 | 用独立测试实例、测试 World 和可重置 fixture 操作已完成的正式功能，试重启、纠正、遗忘及错误身份拒绝 | 对应 M1/M1.x/M2 切片通过自身门禁并获沙箱试用许可；通过只证明该本地范围，不等于真实 Host |
| T3：隔离 Host 试用 | 在独立 Profile/Session 中检查真实对话接线、身份和上下文；先只读，发送与回执分开验证 | 独立 Host 任务、隔离目标和有效授权；当前 `REAL_SEND = NO`，不得由 T1/T2 自动升级 |
| T4：长期本人试用 | 在本人控制的渠道中跨日使用，观察关系、主动性与世界状态是否长期自然 | 真实 Host、发送/ACK、隐私和恢复门禁分别通过后再开放；不把短期演示当长期稳定性证明 |

每个可试切片随交付附一页“试用卡”：启动/重置方式、测试身份与数据来源、3–5 个可亲手执行的步骤、预期观察、已知限制、停用和反馈方法。用户反馈至少分为事实错误、世界不连贯、记忆时机不自然、关系表达失真、打扰感和操作障碍；下一轮先修最影响相处体验的问题。T0/T1 不必等待全部 M1 完成；T2–T4 按各自真实门禁开放。不得为了提前试用在主 Agent、Default Home 或生产聊天中偷偷运行未放行功能。

## 6. 决策点与防跑偏检查

- 每个技术切片都回答：它让上述哪个用户场景更接近可用？若只增强证明而不改变体验，说明其阻断了哪项放行门禁及最小完成条件。
- X1 后若用户仍感觉像“会调用记忆库的聊天机器人”，优先分析检索时机、表达、世界状态和关系演进；不要仅增加字段、场景矩阵或原语试验。
- 正式里程碑同时要求零跨 World 泄漏、零已忘内容正常召回、零无来源的共同经历，并保留用户对自然度、打扰感及“像同一个 Agent”的文字评价。失败记录与成功记录一起保存。
- 规划、静态审核、合成原型、Core CI、真实 Host 验证和实际发送/ACK 各有独立结论；不得相互升级。

本草案的下一项规划交付应是 **X0 场景卡与现状基线**，而不是新的大规模基础设施任务。是否把本校准写入正式 Roadmap、是否授权 X1，均在看到 X0 的具体场景与边界后作独立决定。
