# 开发方式复盘：多代理协作与证据门禁

日期：2026-10-18。观察对象为最近一周及 #56→#57→#61→#58→#59 的代码收口，不把单次经验归纳成已经量化的效率提升。状态：`PROCESS_IMPROVEMENT_PROPOSAL / NOT_EXECUTION_AUTHORIZATION`；本文件不替代 [阶段自主开发合同](CODEX-STAGE-AUTONOMY-PLAN.md)或正式路线的审核/授权规则。

## 保留哪些优点

| 做法 | 已观察到的收益 | 实际证据 / 条件 |
| --- | --- | --- |
| 主协调规划和汇总、实施单写、审核分离 | 减少互相覆盖，复杂任务能持续推进，用户看到统一结论 | #58/#59 整理原功能差异并继承批准修复，审核者独立核对象；不能仅因“另开 Agent”就称独立 |
| 固定 Base / Head / diff / CI | 评审结论有明确适用对象，换基线后不沿用旧绿 | PR CI、实际 squash parent/tree、exact push/main 分开验证 |
| 失败先复现再修复 | 避免随机重跑掩盖确定性问题 | #57 ready 半写窗口被实际 worker 确定性复现，#61 只修两个测试路径 |
| 代码、合成验证、真实 Host、交付分层 | 避免代码可运行被包装为用户体验已完成 | T1 失败、provider 0、T2 阻塞与最终 main 全绿同时保留 |
| 动作意图、回执与幂等恢复 | 配额/会话中断后可查远端，而不重复 merge/push | 本轮 29 项远端动作收口时均 CONFIRMED；旧守护退出后先对账再恢复 |

以上并不证明每项流程都值得在每种改动上重复，也没有对照实验说明节省了多少开发人时。

## 代价和失效模式

**依赖链过深。** #56—#59 在各自父分支开发，主线 Squash 后历史不再相同，发生 add/add 与内容冲突。逐路径 blob/mode 和等价 diff 能证明保留了内容，但证明本身占用审核时间，而且每加入必要修复就需重新推导下游差异。

**治理信息重复。** README、安装入口、当前路线、旧路线与验证索引都各写 CURRENT；更新一处后其他位置继续宣称 Draft 或 NEXT。大量旧合同和否定句压过用户最关心的“现在能用什么、下一步做什么”。

**协调和上下文成本。** 多代理共享历史可能同时带入旧前提；写入边界、任务恢复、额度、watcher、私有回执都需协调。一次状态丢失可能被误当作重新授权。频繁催“继续”和重复报告无变化，会让用户成为人工调度器。

**证明强于体验的偏斜。** Core、设计、探针和 CI 持续增加，但新 Host 环境的普通文本 T1 仍不通过。若继续扩展功能，能力面会扩大，真实可用性却未增长。测试数量和文档数量都不能充当体验进度。

## 建议怎样优化

| 改进 | 具体做法 | 保留的门禁 | 检查结果 |
| --- | --- | --- | --- |
| 单一当前状态入口 | PROJECT-STATUS 记录代码/Host/产品边界与证据；其他指南写本模块用法并引用，不重复维护整张状态表 | 历史合同/验证原件不覆盖；SHA 都标明观察或实现基线 | 每次交付检查新增 CURRENT 是否重复，完整文档索引明确每份用途 |
| 缩短 PR 队列 | 后续功能尽量从刚验证的 main 开始；依赖链目标不超过 2 层，超出时解释必要性；可并行做只读设计/审查 | 不把未授权切片塞进一个大 PR；实际合并仍核固定对象 | 统计从可审核到合并的时间、冲突路径数和基线重审次数 |
| 按风险分配检查 | 文档修改先做全量链接/事实/历史保持检查；代码改动做有意义的针对回归，再运行既有四矩阵 | 本次不改 CI；代码和合并后 exact main 验证不取消 | 后续若提 docs-only CI 路径，单独审核其识别规则与误判负例 |
| CI 性能先观测 | 记录模块耗时、runner/Python/SQLite 版本，区分队列和运行；仅在反复超时证据下评审确定性全覆盖分片 | 不放宽时限、同步强度、平台、竞争次数或断言 | 每个平台覆盖清单/总数一致；缺片、失败、取消均失败 |
| 有界阶段内自主执行 | 一份简短任务书写清范围、动作、预算、验收与停止点；已有许可内完成实施→审核→修复，不每步等待“继续” | 新架构/真实 Host/发送/预算/合并权限只在合同明确时生效；不从路线推权 | 用户介入次数、越界次数、重复同因修复次数及恢复正确性 |
| 按需启用代理 | 主协调持久；A 实施单写；B 固定快照独立审核；真实 Host 阶段才启用 C；任务明确输入、输出和结束点 | B 不替 A 改代码后自审；Host 单写、一次预算计数 | 输出能被另一人/Agent按证据复核，无长期空转代理 |
| 用体验阻断驱动优先级 | 先关依赖隔离与 T1，再小预算 T2，之后决定是否增功能 | 不用模型主观评价替代持久化/隔离检查 | 同 Profile 新进程接续、错误世界拒绝、失败清理均有固定结果 |

这些指标是下一周期拟采集的数据，不是本周已经测出的 KPI；不设无依据的提速百分比或硬交付日期。

## 建议的最小运行节奏

1. 开始：主协调固定目标、Base、范围、动作权限、预算和完成门；A/B 确认输入对象。
2. 开发：A 单写一个可验收增量；B 可提前只读审设计，最终必须重新绑定实际 Head。
3. 纠错：先保留失败原件，按因复现；限定轮次，重复同因或需要新架构则停止汇总。
4. 交付：PR 描述一次说明行为与证据；按现行规则完成独立审核、Ready/Merge 授权和 exact main 收口。
5. 汇总：按里程碑更新用户；等待时显示阻塞的运行，避免把未变化的轮询当作新进展。结束时只更新当前状态入口及直接受影响的指南。

建议的自动账本/报告生成、通知策略、CI 调度变更属于后续开发工具任务。本次仅落地文档分层和索引，不声称这些工具已实现。
