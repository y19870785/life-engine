# LE-RESET-01：从小雪的体验看缺口

当前裁定见 [STATUS](../STATUS.md)。以下场景是建议验收，不是假想的“已发生对话”。`NOW` 仅表示本轮已跑通指定离线入口；`NEEDS_INTEGRATION` 表示已有组件但消费链不完整；`NEEDS_NEW_BUILD` 表示还缺产品机制；`BLOCKED` 表示相应强保证受安全/授权条件约束。测试和实现出处见[能力矩阵](LE-RESET-01-CAPABILITY-EVIDENCE-MATRIX.md)。

## 为什么用户没有感觉提升

这次没有读取你的私密聊天，因此不能诊断某次真实失忆的具体原因。源码和证据能够支持的是一组可检验原因：

1. **用的入口可能根本不是新能力的 consumer。** main 的普通 Host context 走 legacy；本机 provider 的历史对象是 dongxue，不是已证明的微信小雪。应先确认版本与链路，不能要求用户换一种问法掩盖安装差异。
2. **“写进了数据库”还隔着三个门。** 候选是否接受、会话边界是否触发、检索是否命中都可能让下一轮看不到；现在大多只表现成空上下文。
3. **固定演示比真实对话容易。** X1 用固定面试文本；检索原词能命中，同义表达仍失败。模型回答流畅也不能证明它拿到了那条记忆。
4. **开发任务没有持续反馈出口。** 局部测试、修复、打包、安装、真实观察各自完成，仍可能没有同一版本的七天记录。每次谈“完成”都需要重新解释层级，用户只能记得“又多了功能”。
5. **期待的是行为，交付的是容器。** 活动、关系、兴趣字段只是表达基础；有依据的选择、修正和探索还需要可审计的策略及真实互动检验。

这五条是工程解释，不是对用户感受的反驳。接下来的主指标应是“你是否在同一个入口持续用得上”，并能用具体失败定位到记录、接受、检索、注入或表达。

## 每轮怎样判断真的改善

机械验收与人工体验分开计：机械项分别记录保存、来源、可见性、恢复和拒绝结果；人工项分别记录记得、不添事实、不打扰、有用、愿意明天再用，允许 `未观察`。模型输出仅是候选，不能自评后给自己打体验 PASS。

每版保留相同基础任务，再加入 3 条来自用户反馈、脱敏且获准使用的问法。先冻结预期，再比较旧版/新版；错 World 或虚构升格为现实直接否决。自然度不能用固定关键词覆盖率替代，也不设“整体完成百分比”。

首轮建议 7 天、每天 5–10 分钟：前两天跨会话记忆，第三天无关话题，第四天未知细节，第五天换说法，第六天查看来源，第七天重启复验。无需提交整段私密对话；反馈一处好/坏回答即可。没有实际用户反馈的周报写 `USER_FEEDBACK_PENDING`，不自动转下一个能力方向。

可运行的 30 分钟离线脚本和尚需实现的 X2 体验脚本见[X2 方案](../planning/LE-RESET-01-X2-EXPERIENCE-PLAN.md#三十分钟试用脚本)。
